## [Unreleased]

### Fixed

- **Tool-name drift corrected in `quickbooks-online` and `knowbe4` (issue #178, wave 2) — and the audit's own ground truth corrected along the way.** Both plugins now report `DRIFT 0 / UNDOC 0`. The headline is that **the two plugins turned out to have opposite problems**, and taking the static-scan baseline at face value would have got QuickBooks badly wrong.

  **QuickBooks: the reported "46 drifted names" were 45 false positives.** `scripts/tool-drift-audit.mjs`'s static source scans `src/` for `Tool` object literals and `registerTool(...)` calls, and **`qbo-mcp` builds almost all of its tools from a per-entity config** — `generateEntityTools()` emits `` `${config.toolPrefix}_list` ``, `_get`, `_create`, `_update`, `_search` from a template literal (`qbo-mcp/src/entities/generator.ts`), so not one of them appears as a literal the scanner can see. The static ground truth was therefore **19 tools when the server really registers 133**, and every correctly-documented generated name — `qbo_customers_create`, `qbo_accounts_update`, `qbo_journal_entries_create`, and 42 others — was being reported as drift. Re-running with the runtime probe the script already supports (`node scripts/probe-mcp-tools.mjs ~/mcp ground-truth.json`, then `--runtime ground-truth.json`) returns 133 and resolves the union correctly; the count was confirmed independently by importing `dist/entities/index.js` and enumerating `allEntityTools`. **Anyone auditing a generator-driven server must pass `--runtime`; the static scan silently under-reports it, and the failure mode is deleting documentation that was right.** Both vendors were first confirmed to be local sidecars (`containerUrl: http://qbo-mcp`, `http://knowbe4-mcp`) before their local repos were trusted, and QuickBooks' Conduit slug is `qbo`, not `quickbooks-online`.

  **Exactly one QuickBooks claim was genuinely wrong, and it was already documented as absent.** `qbo_invoices_update` does not exist — the invoice config declares `get` and `create` plus hand-written `list`/`send` extras, and no `update` (`qbo-mcp/src/entities/invoice.ts`) — and `GOVERNANCE.md`'s *Known sharp edges* already said so. The sentence has been rewritten so it states the absence without naming a phantom tool in backticks, and extended: customers has the same gap (`list`/`get`/`create`/`search`, no update), and an agent must not treat a missing `_update` as a naming problem it can guess around. **The 69 real tools no document mentioned are now inventoried in `README.md`**, generated from the server's own registry so the table cannot drift from it, along with two behaviours that are invisible from the names — `qbo_customers_list` and `qbo_invoices_list` *elicit* when called with no arguments rather than returning the whole book, and every `_update` is a sparse update needing the record's current `SyncToken`. Two tiering gaps found while reconciling `GOVERNANCE.md` against the real 133: **`qbo_vendor_credits_create`/`_update` and `qbo_sales_receipts_create`/`_update` appeared in no group at all.** Vendor credits are now in Write and sales receipts in the money-moving set, each with re-derived reasoning — a sales receipt books revenue *and* cash in one document, so a mistaken one overstates income and the deposit account without ever entering accounts receivable where an AR review would catch it; a wrong vendor credit surfaces as an underpayment to a supplier rather than as a visible QBO error.

  **KnowBe4 was the real drift case: 27 wrong names across 36 documented, and 25 of the 34 real tools undocumented.** The docs described a substantially different server. 17 names were renames with a genuine equivalent (`knowbe4_phishing_list_campaigns` → `_phishing_campaigns_list`, `_training_list_enrollments` → `_training_enrollments_list`, `_groups_list_members` → `_groups_members`, `_training_list_store_purchases` → `_store_purchases_list`, and so on). **Ten were capabilities that do not exist and were deleted rather than mapped to a near-miss**, each replaced by a statement of what is really available: the three `knowbe4_phisher_*` tools (PhishER is a separate KnowBe4 product, entirely unexposed), phishing template browse/get, training module browse/get, per-user event history, PPP-trend, and department breakdown.

  **Four proposed renames were rejected because the nearest match would have changed the meaning silently.** The audit's own suggestions are recorded here because each is plausible and each is wrong. `knowbe4_reporting_ppp_trend` → `knowbe4_account_risk_score_history`: risk score and phish-prone percentage are different measures on different scales, and a risk-score line presented as a PPP trend is wrong in a way no client can catch. `knowbe4_reporting_department_breakdown` → `knowbe4_groups_list`: KnowBe4 groups are membership lists that may or may not correspond to departments, while `department` is a free-text field on the user record — reporting group risk under department headings misstates who the numbers describe. `knowbe4_users_list_events` → `knowbe4_users_list`: that turns "this user's phishing and training history" into "list all users"; the real per-person behavioural data lives in per-PST recipient records. `knowbe4_phishing_list_templates`/`_get_template` → `knowbe4_phishing_campaigns_list`/`_get`: a campaign is not a template. **One row was also split rather than renamed** — the documented `knowbe4_phishing_list_security_tests` ("security tests *for a campaign*", parameter `campaign_id`) matches `knowbe4_phishing_campaign_tests` by behaviour but `knowbe4_phishing_security_tests_list` by name, and those are two different real tools; both are now documented with the distinction stated.

  **Parameter drift mattered as much as name drift, and changed the shape of several documented workflows.** Verified against the shipped input schemas: `knowbe4_training_enrollments_list` has **no `campaign_id` and no `status`** (it is account-wide, so "overdue enrollments for the HIPAA campaign" is a full paginated read filtered client-side, not a query); the three `knowbe4_reporting_*` tools take **no date range at all** and `knowbe4_reporting_risk_overview` takes no arguments; `knowbe4_users_list` filters only by `status` (`active`/`archived`) and `group_id`, with no risk-level filter; and the recipient tools are scoped to one Phishing Security Test, so `knowbe4_phishing_security_test_recipient` needs **both** `pst_id` and `recipient_id`. Two new hazards were derived from the source rather than transplanted: **the reporting summaries are page-scoped and do not say so** — `knowbe4_reporting_phishing_summary` describes itself as fetching all PSTs but reads a single page (default `per_page=500`) and averages over it, returning `average_phish_prone_percentage` as though it were account-wide (`knowbe4-mcp/src/domains/reporting.ts:75-125`), with `knowbe4_reporting_training_summary` behaving the same way — and the list-tool default is `per_page=100` against a ceiling of 500, so an unattended agent paginating a large account spends five times the requests it needs from a ~1,000/day budget shared across every technician on the tenant. `GOVERNANCE.md`'s claim that `knowbe4_reporting_*` "answers most MSP reporting questions at department granularity" was **false against the real surface** and has been replaced.

  **KnowBe4 is genuinely read-only, and the claim is now backed by evidence rather than inherited.** Verified at the transport layer: the shared client accepts a `method` option but every domain call leaves it at the default `GET`, and there is no `POST`/`PUT`/`PATCH`/`DELETE` anywhere in `knowbe4-mcp/src/domains/`. The claim was actually *strengthened* by the deletions — the previous `security-awareness-analyst` agent described a PhishER triage workflow that purged mail from customer mailboxes and blocked senders, i.e. **the plugin's own agent documented destructive capability that its governance doc said did not exist**; no such tool has ever shipped, and that workflow is gone. Newly documented in `GOVERNANCE.md`: `knowbe4_navigate`/`knowbe4_back` are refused by Conduit before any tier check (`conduit__my_access` replaces them), and four meta-tools including the `knowbe4_execute_tool` **dispatcher** exist only under `LAZY_LOADING=true` — the dispatcher does not widen the surface, since the pool it dispatches into is the same read-only set, but a name-based allowlist should not assume it is absent. `knowbe4` still has no `VENDOR_TOOL_CONFIG` entry, so every tool continues to enforce at `admin`; `qbo` still has exactly four classified `read` entries, so all of QuickBooks' reports remain behind `admin`. Both statements were re-verified against `conduit/src/proxy/result-cache.ts` rather than carried over.

  Two plugins patch-bumped: `quickbooks-online` 0.2.8, `knowbe4` 0.2.6.
- **The drift audit was blind to a whole tool-declaration style, and `scalepad`'s "109 drifted names" were an artefact of it.** `scripts/tool-drift-audit.mjs` found tools two ways: `Tool` object literals with a `name: "…"` next to an `inputSchema`, and `server.registerTool("…")` calls. Neither sees a server that declares its tools through a **local factory helper** — `function ro(name, description, inputSchema, call) { return { tool: { name, description, inputSchema }, call }; }`, then `ro("scalepad_core_clients_list", …)` — because there is no `name:` literal in the file at all. `scalepad-mcp` writes two of its five domains that way, so the scanner reported **164 tools when the server serves 381**: it read `backup-radar.ts`, `controlmap.ts` and `quoter.ts` (raw object literals, 164 between them) and got **zero** hits from `core.ts` (24) and `lifecycle-manager.ts` (193). The audit then compared 203 correctly-documented names against a truth set missing 217 of them and called 109 of them drift.

  The scanner now also detects factories: a local function whose signature declares both a `name` (first) and an `inputSchema` parameter is a tool builder, and its call sites' first string argument is a tool name. Factories are collected across the whole `src/` tree before call sites are scanned, so a repo that declares the helper in one module and calls it from another is covered. Verified two ways — the fixed scanner's 381 names match, exactly and with no false positives, an independent enumeration that loaded each compiled domain handler and read `getTools()`; and across the other 63 plugins the fix changes **nothing** (no other server in the fleet currently uses this shape, so this is a latent-blindness fix, not a re-count).

- **`scalepad` had no tool-name drift — but its governance doc was describing a permission model that changed underneath it, and 178 of its 381 tools were undocumented (issue #178).** With the scanner fixed, all 203 documented names verify against the server and the audit reports `DRIFT 0`; no rename was applied and no claim was deleted, because none was wrong. What was wrong was everything around them.

  **`GOVERNANCE.md` documented the pre-2026-08-04 Conduit classification, in which ScalePad's tiers were inverted.** Conduit then classified 41 ScalePad tools and every one was a delete, a revoke or a publish; because an unclassified tool fail-closes to `admin`, `write` bought only the ability to destroy and `read` bought nothing. Conduit now classifies **all 381 — 177 read, 201 write, 3 admin** — so the doc's central warnings ("tier `read` gets you nothing", "tier `write` gets you the 41 deletes and nothing else", "`admin` is what asset reporting requires") were each the opposite of current behaviour. Re-derived against the live table, with an explicit note that **grants made before 2026-08-04 should be re-checked**: an owner who needed asset reporting had to pick `admin` then, and that grant still says `admin`.

  **One risk finding changed shape rather than wording.** The doc flagged the deliverable share links as "split across two tiers, backwards" — `_revoke` classified at `write` while `_create`/`_regenerate` fail-closed to `admin`. All three are now uniformly `write`, so that inversion is gone. What the doc missed is a **fourth** share-link tool: `scalepad_lm_deliverables_share_link_get` returns the live, unauthenticated URL and is tier **`read`**. Minting the link is gated; reading out the already-minted link is not, so a read-only agent summarising deliverables can emit a working share URL into a transcript. The hazard moved from a write-tier ordering bug to a read-tier disclosure one.

  **The two credential-minting tools are now documented as such everywhere they appear.** `scalepad_quoter_auth_authorize` and `scalepad_quoter_auth_refresh` carry **no** MCP annotations — the server itself reports them read-only, because from its point of view they read a token rather than write a record — yet they `POST` to **`api.quoter.com`, the only host in this plugin that is not ScalePad**, through an HTTP client with no auth configured, and return an `access_token` plus a `refresh_token`. `_authorize`'s `client_id` / `secret` arguments are optional and, when supplied, **override the configured credentials**. Conduit pins both to `admin` by hand for exactly this reason. They are now called out in `GOVERNANCE.md` (a dedicated section), the `quoter` and `api-patterns` skills, the `quote-builder` agent (which is told not to call them at all — the server handles the exchange), and `README.md`, each stating the same three things: different host, credential-overriding arguments, and a response that is a bearer credential sitting in model context with no useful expiry. `scalepad_lm_enrollment_tokens_create` is the third `admin` tool and is documented alongside them.

  **All 381 tools are now named in the docs** (`UNDOC 0`, from 178) via a new `references/tool-inventory.md`: every tool with its read/write classification, enforced permission tier, and resolved HTTP verb and path. The read/write split is derived, not guessed — the server annotates exactly its 202 mutating tools and none of its 179 read-only ones, cross-checked against every tool's resolved verb (no mutating tool uses `GET`). Per-domain counts in the README and skills are now exact (24 / 193 / 98 / 3 / 61 + 2 helpers) rather than "~190" / "~100" / "~60" / "roughly 400". Also recorded as *absent*, since it is the first thing a review looks for: there is no arbitrary-request surface — zero tools with `additionalProperties: true`, no `raw_request`/`execute_tool`/passthrough, and the SDK builds every URL from a hardcoded path template — so no call's blast radius is chosen by argument rather than by name.

  **The governance doc's marquee risk claim was wrong about the real tool, and is now right about it.** `proofpoint_forensics_search_destroy` never existed; the capability is `proofpoint_forensics_pull_messages`, and the previous revision already flagged the name while keeping the analysis. The asymmetry that makes it easy to miss is documented too — the sibling `spamtitan_get_stats` **does** take `domain`, so the queue reads as though it should. Each plugin keeps its existing path shape, because **Conduit serves both**: the unified endpoint is registered by `unifiedProxyRoutes` (`src/proxy/unified-router.ts:506,545`) and the per-vendor endpoint by `proxyRoutes` (`src/proxy/router.ts:103`), which is marked deprecated and answers with `Deprecation: true` plus a `Link: …/v1/mcp; rel="successor-version"` header but is live and registered in `src/index.ts:1535`. **The path segment is not cosmetic** — the per-vendor route resolves it through `getVendor()`, a direct `VENDORS` key lookup, and returns `404 Unknown vendor` on a miss, so a repointed URL carrying a plugin-directory name that is not the Conduit slug would look right and fail. All nine vendor slugs were checked against the `slug` field in `src/credentials/vendor-config.ts` and **all nine match their plugin directory name exactly** — no `it-glue`→`itglue`-style divergence in this set, and no plugin in the ten is missing from `vendor-config.ts`. Ten plugins patch-bumped: `auvik` 0.1.5, `blackpoint` 1.1.6, `crewhu` 1.0.6, `freshdesk` 1.0.7, `immybot` 1.1.6, `inforcer` 1.0.6, `saas-alerts` 1.0.6, `threatlocker` 0.1.6, `timezest` 1.1.7, `wyre-gateway` 1.4.2

- **Security-vendor `GOVERNANCE.md` tier tables realigned to Conduit's real model — `huntress`, `sentinelone`, `threatlocker`, `blackpoint`, `cipp`, `saas-alerts`.** First batch of the taxonomy-debt cleanup `wyre-gateway/GOVERNANCE.md` flagged. All six shipped a **Read / Write / Destructive** table, which matches neither Conduit's enforcement tiers (`read`/`write`/`admin` plus `none`, `src/access/permission-tier.ts:27`) nor the four groups its access editor presents (`read`/`write`/`delete`/`admin`). Every documented tool has been re-tiered against `VENDOR_TOOL_CONFIG` (`src/proxy/result-cache.ts`) using the stated convention — `isAdmin → admin` (outranks), `isWrite → write`, neither → `read` (`tool-classification.ts:33-38`) — and each table now carries an explicit `Enforcement tier` column. **158 documented tools re-tiered; 90 land in a different bucket than the old table put them** (41 classified tools that moved, plus 49 Conduit has never classified). The risk commentary is kept as prose and, where the mechanical tier disagrees with the author's judgement, both are stated. **All six per-call-approval promises deleted** — Conduit has no approval step, no confirmation, and no elicitation; each file now says so and names per-call approval as a policy the reader imposes on their agents. **The reviewer's priority — tools an author called destructive that enforce at `write`:** `huntress_incidents_bulk_approve` and `huntress_incidents_bulk_reject`, and only those two, fleet-batch-wide. Approving a Huntress remediation acts on a customer endpoint, and Conduit classifies it `write` because the effect is bounded to the vendor-authored plan and carries no operator code (`result-cache.ts:824-831`) — so **anyone holding `write` on Huntress can order endpoint remediation across a customer's fleet with no further gate.** **Two findings that invert the expected story.** First, the Delete presentation group is **empty for all six vendors** — every delete-verb tool in the batch is `isAdmin`, so it needs `admin` and a `write` grant never reaches it; the "granting `write` also grants delete" mechanism is stated in each file but is not what bites here.
