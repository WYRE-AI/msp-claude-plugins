# Changelog

All notable changes to the MSP Claude Plugin Marketplace will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed

- **Four plugins renamed to match their Conduit vendor slugs: `it-glue` → `itglue`, `quickbooks-online` → `qbo`, `ninjaone-rmm` → `ninjaone`, `checkpoint-avanan` → `avanan`.** Conduit's skills-catalog sync links a pack to its vendor only when the marketplace entry name equals the vendor slug in Conduit's registry (`catalog-sync.ts` sets `vendorSlug` on exact match, nothing else). These four packs were syncing with no vendor linkage, so they missed vendor-follow access grants and fell back to default-allowed-for-all-members. The rename is the whole fix — no skill content changed.

  The human-readable names survive as the new `displayName` marketplace field, which `generate-plugins.ts` now prefers over its `nameMap`/humanize derivation (otherwise `qbo` would render as "Qbo" on the docs site). Directory names deliberately did not move — `kaseya/it-glue/` stays put — because cross-plugin skill references are canonical `<marketplace name>-<skill slug>`, so the rename rewrote 152 reference tokens across 96 files (`it-glue-configurations` → `itglue-configurations` and kin), which is also why nearly every plugin carries a patch bump. Anyone who installed under the old names re-installs once under the new ones.

### Added

- **New `proofpoint-essentials` plugin (marketplace 1.32.0), a sibling to the existing `proofpoint` (TAP) plugin covering a different product entirely.** Proofpoint Essentials is Proofpoint's SMB/MSP-tier email security product — a separate API, base URL, and credential model from Proofpoint TAP (`X-User`/`X-Password` org-admin header auth against `{region}.proofpointessentials.com`, not TAP's service-principal HTTP Basic Auth against `tap-api.proofpoint.com`). The two plugins are unrelated in every way that matters except vendor name, so `proofpoint` was left untouched. Ships 4 skills (`api-patterns` covering auth, regional pod resolution via endpoint discovery, and batch-create 207 multi-status handling; `org-management` covering org lifecycle, domains, features, licensing, and package tier; `user-management` covering mailbox user CRUD including batch create; `reporting` covering inbound/outbound mail-flow time-series) and 2 commands (`/search-org`, `/org-health-check`). The companion `proofpoint-essentials-mcp` server is under active development and not yet published — tool names throughout follow the `proofpoint_essentials_{resource}_{operation}` convention the server is being built to, so the docs will be accurate on day one. No `.mcp.json` ships with this plugin, matching its `proofpoint`/`knowbe4` email-security siblings, since there is no live gateway wiring yet.

- **New `nutanix` plugin (marketplace 1.29.0) and the `infrastructure` category it introduces.** Backed by Nutanix's official v4 API MCP server ([ntnx-api-mcp-server](https://github.com/nutanix/ntnx-api-mcp-server), pinned v0.8) behind the Conduit gateway. The plugin documents the real tool surface — 4 discovery tools (`listOperations`, `getOperationSchema`, `getCodeSample`, `getOperationPermissions`) plus up to 19 `<namespace>_execute` executors, not per-entity CRUD — and teaches the canonical discovery → schema → execute workflow everywhere. Ships 6 skills (`api-patterns` with a full 19-namespace REFERENCE, `vm-management`, `cluster-operations`, `storage`, `networking`, `monitoring-aiops`), 5 commands (`/find-vm`, `/vm-inventory`, `/cluster-health`, `/capacity-report`, `/storage-usage`), and 2 agents (`nutanix-infra-expert`, `nutanix-capacity-planner`). All documentation states the deployment's server-side `READ_ONLY_MODE=true` — non-GET operations are blocked, so no skill, command, or agent promises a write workflow — and that credentials (Prism Central host + username/password or API key) live in the Conduit gateway UI, not local env vars, so the plugin carries no `.mcp.json` or `.env.example`. The `infrastructure` category was added to `VALID_CATEGORIES` in `docs/scripts/generate-plugins.ts` and to the plugin catalog page's section list and label map.

- **Retirement notice for `mcp.wyre.ai` and a migration guide at `/migration`.** The hosted gateway at `mcp.wyre.ai` retires on **30 September 2026**, at which point the domain redirects to `conduit.wyre.ai` and stops serving MCP traffic. `RetirementBanner.astro` renders from `BaseLayout.astro`, so every page on the site carries the notice — index, docs, and all plugin and MCP-server detail pages. It is deliberately not dismissible: the cutoff is a hard one, and a banner someone can hide is a migration they can miss.

  `src/pages/migration.astro` is the customer-facing guide the banner links to. Organisations, members and their roles, and service accounts are migrated for customers. Vendor credentials are **not** transferred — every connection's API key, token or OAuth grant is re-entered once in Conduit — and neither are MCP client connections, because the access token a client holds was issued by the old gateway's OAuth server and Conduit will not accept it. The guide says plainly that the redirect is a safety net for browser traffic and not a migration path, so nobody plans around the old URL continuing to work for `tools/call`.

  Note that this site is baked into the gateway image at build time (`mcp-gateway`'s Dockerfile clones this repo into `public/`), so the banner reaches `mcp.wyre.ai` only after a gateway rebuild and prod promote — merging here is not enough on its own.

- **Two CI guards that close the documentation-integrity classes #181, #196, #202 and #205 each fixed by hand.** Those four PRs repaired references to things that no longer exist — a deleted skill still routed to from other plugins, and 86 references naming skills that never existed because five plugins have a directory name that differs from their marketplace name. Nothing prevented the next one. `scripts/check-doc-references.mjs` and `scripts/check-tool-anchoring.mjs` now run on every PR from `.github/workflows/validate.yml`, in **0.24s combined**. `scripts/tool-drift-audit.mjs` stays out of CI deliberately: it needs the sibling `*-mcp` checkouts, which the runner does not have.

  **`check-doc-references.mjs` derives canonical ids from `marketplace.json`, never from directory names** — that inversion *is* the #181 bug. A skill's id is `<marketplace entry name>-<skill directory slug>`, so `connectwise/manage` yields `connectwise-psa-*`, `quickbooks/quickbooks-online` yields `quickbooks-online-*` and `shared` yields `shared-skills-*`. 1,526 backticked skill-shaped references across 1,214 files are resolved against 1,215 ids from 76 plugins, plus three structural rules: every marketplace `source` resolves to a real directory and every on-disk plugin is registered; the generated `docs/src/data/plugins.ts` may not claim a skill, agent or command that is not on disk; and the hand-maintained routine-catalog table may not name a plugin or agent that does not exist.

  **The hard part is telling a skill reference from a hyphenated tool name, which is where #181 hit ~34 false positives.** `pandadoc-send-document` and `pax8-list-companies` are tools. Both shapes are `<plugin>-<words>`, so the discriminator is the tail: a skill slug names a subject area (`tickets`, `time-entries`, `api-patterns`), a tool name leads with the verb it performs. A token counts as a reference only when its prefix is a known plugin alias **and** its tail is either a slug that really is a skill directory somewhere, or — inside an `## Anti-triggers` section, whose bullets exist for no other purpose than naming another skill — any noun-led tail. The second branch is what catches references to a skill whose slug survives nowhere after deletion. On the current tree that is 1,526 candidates and **zero** false positives.

  **`CHANGELOG.md` is excluded, because a changelog's job is to name what was removed.** "`syncro-msp` → `syncro`" and "#195 deleted `checkpoint-avanan-incidents`" are correct precisely because they no longer resolve.

  **`check-tool-anchoring.mjs` covers the class that `DRIFT 0` cannot see.** The drift audit compares *named* tools against the server, so documentation naming no tool passes every check no matter what it claims — which is how checkpoint-avanan's four commands shipped a fabricated REST API and invented flags. The new check flags any skill, agent or command carrying an HTTP verb-and-path or a CLI-style `--flag` while naming zero backticked `lower_snake_case` tool tokens (the same extraction `tool-drift-audit.mjs` uses, so the two agree on what "names a tool" means).

  **It is a ratchet, not a cliff.** 158 of the repo's 780 skills/agents/commands were already un-anchored — `autotask`'s `crm` skill documents `POST /v1.0/Companies` and names none of that plugin's 108 tools; `syncro` has 15 such commands. Rewriting them needs per-vendor ground truth CI does not have, so they are inventoried in `scripts/unanchored-docs.json` with the evidence line that put each one there. The check fails on any unit **not** listed, and on any listed unit that is gone or now names tools — so, like `conduit/src/access/tool-naming-exceptions.ts`, the file cannot rot and the list can only shrink. Every run also emits a `::warning` carrying the outstanding count, so the debt stays visible rather than silently accepted.

  **What it deliberately does not attempt:** whether an un-anchored REST recipe is *true*. Syncro's commands document Syncro's real API; checkpoint-avanan's documented a fiction. Nothing in the text separates them — that is exactly the job `tool-drift-audit.mjs` does with vendor ground truth.

  **Both guards were mutation-tested against the real defects rather than invented ones.** Replaying the tree as it stood before each fix, the reference check reports 67 dangling references across 20 ids at #181's parent, `checkpoint-avanan-incidents` and `checkpoint-avanan-policies` at #196's, `abnormal-security-account-takeover` and `domotz-eyes` at #202's, and both the stale generated data and the routine-catalog row at #205's. Restoring checkpoint-avanan's four pre-#204 commands plus the deleted `manage-policy` makes the anchoring check name all five, quoting `POST /app/hec-api/v1.0/quarantine/release` and `--allow-list` back.

### Fixed

- **Corrective pass on #178's remaining confirmed tool-name drift, plus two plugins the live audit caught outside its original scope.** Re-running `tool-drift-audit.mjs` against #178's 18-vendor confirmed-drift list before touching anything showed 14 already fixed by prior PRs (#197, #198, #200, #201) — real work remained in six places. **`rootly`** was the worst case in the fleet and had never actually been fixed: the gateway routes it to the hosted `mcp.rootly.com` server (253 tools), not the local `rootly-mcp` repo, and four skills (`postmortems`, `services`, `alerts`, `workflows`) documented a fictional API surface — 0% of their tool names existed on either upstream. All four were rewritten against Rootly's real OpenAPI spec (retrospectives replace the invented postmortem lifecycle, real `service`/`alert`/`workflow` schemas replace invented tier/condition/action fields), `api-patterns` and `incidents` got the confirmed renames, and both agents gained `mcp__rootly__*` frontmatter they were missing entirely — meaning neither could previously call Rootly at all, corrected names or not. **`freshdesk`, `timezest`, `connectwise/manage`** had small residual drift the earlier bulk passes missed (a few shorthand tool references, one sentence a naive token-swap would have made self-contradictory). **`kaseya/it-glue`**'s one confirmed-drift item turned out to be a false positive — the wrong name only ever appeared inside a "not X" warning — but the live audit surfaced 4 real phantom "location" tools nearby (`create_location`, `get_location`, `search_locations`, `update_location`) that #178 never flagged. Re-running the fleet audit live (rather than trusting #178's static tables) also caught drift in two plugins outside its original list: **`kaseya/autotask`** had 2 fictional contract tools from a recent addition (#212), one of which the audit script's own similarity heuristic missed entirely; **`mailprotector`** had 3 genuine renames, with 6 of the audit's 9 flagged names turning out to be real SDK field/enum names once checked against `mailprotector-mcp` source directly, not tool references at all — a false-positive class worth remembering next time the script's output gets applied mechanically instead of verified. Every fix in this pass was independently checked against real ground truth (server source, live gateway tools, or `tool-drift-audit.mjs` itself) before being applied. `checkpoint-avanan`'s governance gap, the fleet-wide undocumented-tools pass, and `pax8` remain open — out of scope for a rename-only pass.

- **The two claims the previous pass flagged and left open are now resolved, and the drift audit no longer manufactures the drift that hid them.** The last entry closed by recording two things it could not verify — `xero`'s Custom Connections bullet and `warmly`'s missing Conduit entry — and the audit stood at `drifted=3 clean=45 unverified=16`. All three "drifted" vendors were artifacts of the scanner, not fabricated tool names. With the two stale server checkouts refreshed and a runtime probe supplied, the same audit reports **`drifted=0`**.

  **`xero`: the plugin was wrong, Conduit was right — and the error was in three places, not one.** `conduit/src/credentials/vendor-config.ts` gives Xero an `oauthConfig` with `authorizeUrl: https://login.xero.com/identity/connect/authorize` and a scope list ending in `offline_access` — a browser-consent authorization-code flow whose defining scope is the one that yields a refresh token. `vendor-oauth.ts` names Xero in its module docstring, implements the `grant_type: refresh_token` exchange, persists `refreshToken`, and `credential-injector.ts` refreshes proactively 60s before expiry with a reactive 401-retry path behind it. The string "Custom Connection" appears **nowhere** in Conduit or `xero-mcp`. Custom Connections is a different Xero product — `client_credentials`, single-organisation, no authorize leg — so the first bullet was describing a flow this integration does not use, and it **contradicted the bullet directly beneath it**, which already said "Conduit refreshes the token itself as it nears expiry". Two further mentions were corrected: Xero history attributes changes to the connected app, not to a Custom Connection; and "a Custom Connection token can address multiple organizations" was backwards twice over, since single-org binding is precisely what Custom Connections enforces — as this plugin's own `README.md` already states — and multi-org addressing is what the standard grant permits. That last bullet also gained a warning the document did not previously carry: Conduit does not offer a tenant choice, it calls `https://api.xero.com/connections` at connect time and stores the **first** tenant returned (`fetchXeroTenantId`), so an operator who can see more than one Xero organization should confirm the stored tenant before anyone is granted the write tools.

  The plugin's `README.md` and `api-patterns` skill still describe Custom Connections, and were deliberately left alone: they document the direct, self-managed path where the operator holds `XERO_CLIENT_ID`/`SECRET` themselves, and their description of that product — `client_credentials`, 30-minute tokens, no refresh, one organisation — is correct. Only the claims about what *Conduit* does were wrong. The two documents do describe different deployment models, which is worth a separate look.

  **`warmly`: the plugin's `GOVERNANCE.md` asserted a Conduit connection that does not exist.** `grep -ci warmly` against Conduit's `vendor-config.ts` returns **0** — not a hidden entry, not a disabled one, none. The connector is wired only in the older `wyre-technology/mcp-gateway` registry (`warmly:`, plus its OAuth wiring and bicep). PR #206 had already found this and correctly declined to repoint the README, but the `GOVERNANCE.md` still opened "It reaches Warmly through the WYRE Conduit gateway (`https://conduit.wyre.ai/v1/mcp`)", and the tier blockquote said the only way to use the plugin "today" was an `admin` grant — when no grant of any tier reaches it. Both files now lead with an unmissable note, the README's connection section is retitled to name the legacy gateway explicitly and warns against substituting `conduit.wyre.ai` for a slug Conduit does not know, and the tier blockquote is scoped to the day the vendor is brokered. **The plugin ships no `.mcp.json`, so nothing was ever misrouted** — the defect was documentation, not wiring. `slack` and `stripe` are in the same position (zero Conduit entries) but make no such claim, having no `GOVERNANCE.md` at all.

- **`scripts/tool-drift-audit.mjs` no longer reports drift it cannot substantiate, and says so out loud instead.** All three drifted vendors were scanner artifacts, in two distinct ways, and the report rendered both identically to a fabricated tool name — the reader had no way to tell them apart.

  **Stale checkouts (`kaseya/it-glue`, 4 names; `kaseya/datto-rmm`, 1).** The static scan reads whatever is on disk under `--servers`. Both local `*-mcp` clones predated the commits that added the "missing" tools — the IT Glue checkout was old enough to still have `src/index.ts` where upstream now has `src/mcp-server.ts`. `create_location`, `get_location`, `search_locations`, `update_location` and `datto_find_device` are all real upstream, and both plugins documented them correctly all along. Cloning the two repos fresh dropped the audit to `drifted=1` with no documentation edit. **The script cannot detect this itself** — knowing a checkout is behind requires a fetch, which it does not do — so it now prints the exact `git -C … pull --ff-only` commands whenever a drift verdict rests on static evidence alone, and the header documents the failure mode as a first-class hazard.

  **Generator-driven servers (`quickbooks-online`, 114 names).** `qbo-mcp` builds tool names from a per-entity config as `` name: `${config.toolPrefix}_list` ``, so the literal-name pass read straight past them: the scanner saw 19 tools where the server registers 133, and every one of the 114 correctly-documented names looked fabricated. Given the choice between teaching the scanner to evaluate template literals and making it refuse to judge, it now refuses — resolving one repo's interpolation pattern would not stop the next generator-driven server from silently under-extracting in a new one. When the scan finds a tool name built by interpolation, or extracts nothing at all from a `src/` tree, it marks the vendor `PARTIAL-static` and reports it as **unverifiable rather than drifted**, naming the file and line that proved the incompleteness. Supplying `--runtime` resolves it properly: the stdio probe returns qbo-mcp's real 133-tool surface and drift falls to zero.

  **The same fix caught a false *clean*, which was the more dangerous bug.** An empty extraction was truthy, so `sentinelone` — where the scan found zero tools — was being counted as verified-and-clean against a ground truth of `[]`. It is now correctly unverifiable: `sentinelone-mcp` is a multitenant HTTP shim that spawns `sentinel-one/purple-mcp` per tenant and registers no tools of its own, so neither the static scan nor the stdio probe can ever see its surface.
- **Four documentation references that pointed at nothing, found by the new guards on their first run.** Each is the exact class the guards exist to prevent, and each had survived the entire correction pass.

  **`checkpoint-avanan`'s exceptions skill routed "Mimecast managed senders" to `mimecast-policies`, which has never existed.** The Mimecast plugin ships four skills — message tracking, delivery queues, threat intelligence and API patterns — and none of them covers managed senders. The bullet now says so rather than sending the reader to a skill that was never written. Plugin patch-bumped to 0.4.2.

  **The docs site's agent routine catalog named four plugins by their directory instead of their marketplace name** — `connectwise-manage` (×3), `quickbooks` (×2), `superops-ai` (×2) and `syncro-msp` (×2). A reader taking those into `/plugin install` gets nothing; the installable ids are `connectwise-psa`, `quickbooks-online`, `superops` and `syncro`. Only the **Plugin** column was corrected: the adjacent **Connector** column is a Conduit vendor namespace where `connectwise-manage` really is the vendor id, and it already differs from the plugin column elsewhere in the same table (`threat-report-generator` / `abnormal-security` / `abnormal`).

  **The two skills whose `name:` frontmatter disagreed with their canonical id are renamed, closing the hole #181 flagged for follow-up.** `connectwise/manage/skills/tickets` was named `connectwise-manage-tickets` and `ninjaone/ninjaone-rmm/skills/devices` was named `ninjaone-devices`. A second id for the same skill is what let *some* of #181's malformed references resolve while their siblings dangled — and it defeats the new guard directly: with the alias present, reintroducing `connectwise-manage-tickets` into a live anti-trigger bullet passes. Both now carry the prose title every one of their siblings already uses ("ConnectWise Manage Tickets", "NinjaOne Devices"), and the guard asserts that any slug-shaped skill `name:` equals its canonical id. 18 of 341 skills use slug-shaped names; the other 16 already conformed. No reference anywhere in the repo used either old alias, and the docs generator reads the directory slug, not `name:`, so no regeneration is needed. Plugins patch-bumped to 0.3.5 and 0.2.8.

- **Every revocation and rotation claim in this marketplace is now true, because the underlying gaps were fixed first.** 63 governance documents told MSP owners that "revoking gateway access revokes vendor access with it, immediately" and that "credential rotation happens once at the gateway". **Both were false when written.** `wyre-technology/conduit#1303` (merged 2026-08-06) made most of the first one true; this pass makes the documents match the code, and corrects the second one, which #1303 did not touch and which was overstated in a different way than expected.

  **The revocation claim: 38 per-vendor documents rewritten, plus `wyre-gateway/GOVERNANCE.md`.** #1303 introduced a single deprovisioning primitive (`conduit/src/auth/deprovisioning.ts`) called from every teardown path — console member removal, reseller operator removal, SCIM deactivate and delete, org hard-delete/soft-delete/suspend — which revokes gateway refresh tokens and clears per-vendor access grants. `revokeAllUserTokens` had previously had **zero callers**, so a removed member's 30-day refresh token kept minting fresh 1-hour access tokens indefinitely. `users.active` was written by SCIM and read by **nothing**; it is now read at four layers (auth-code grant, refresh grant, `injectCredentials`, and the browser session). The refresh-grant check sits *after* rotation destroys the presented token, so a deactivated user's refresh chain terminates rather than being refused once. An invariant test now source-scans for membership-teardown SQL and fails any file that tears membership down without revoking.

  **Two of the fixes were worse than they looked.** SCIM's teardown ran on the NOBYPASSRLS request pool with `conduit.current_user_id = ''`, and every table it touches gates its DELETE on that GUC — so **every DELETE matched zero rows and reported success.** SCIM deprovisioning had never actually deprovisioned; it only appeared to. Separately, the console session was a pure signed-cookie decode with no DB read at all, so a user deactivated in the IdP kept **full console access for up to 30 days** — reading and rotating org credentials, granting vendor access, inviting members — a strictly higher-privilege surface than the MCP endpoint.

  **The residual gap is stated rather than rounded away.** An already-issued access token is still a stateless HS256 JWT with no `jti` and no denylist, so it survives to its `exp` — one hour by default. A user *deactivated in the IdP* is refused on their very next request at all four layers; a user *only removed from an organisation* keeps that token for up to an hour, during which it can reach **only connections they made personally with their own key**, never the org's, because org, team and role are resolved from live membership on every request. The per-vendor wording says exactly that in two sentences and links to `wyre-gateway/GOVERNANCE.md` for the full treatment.

  **The rotation claim was overstated for 60 of 98 vendors — and in a second way for all of them.** Conduit's auth taxonomy is derived, not declared: the only discriminator is whether a vendor entry carries an `oauthConfig` (`isOAuthVendor`, `vendor-config.ts:6538`). **38 vendors are OAuth** and get genuine automatic token refresh (proactive at 60s-to-expiry, plus a reactive 401 → refresh → retry-once), with write-back to whichever scope the key came from. **For the other 60 there is no rotate action at all** — no HTTP route, no console control, no CLI command; the only `rotate` action in the entire product is for a tunnel enrolment token. Rotation means re-submitting the connect form, which upserts the row, and nothing tracks credential age or warns before a secret expires. Conduit's own docs already said so; the governance documents did not.

  **"Once at the gateway" is also once per *scope*, not once per vendor.** A vendor credential can exist in five places simultaneously — personal, org anchor, named org key, legacy team, and service client — and resolution prefers personal first. So **a technician who connected the vendor personally is entirely unaffected by an org rotation**, and rotating the anchor does not propagate to named keys hanging off it (`ensureOrgAnchor` is `ON CONFLICT DO NOTHING`). There is no fan-out and no admin view that enumerates every stored copy. That is now stated in `wyre-gateway/GOVERNANCE.md` rather than implied away by "once".

  **The result-cache bullet was re-verified and still holds, with two corrections that make it less alarming.** #1303 did not touch the cache; `CacheStore` exposes no delete operation at all, and `invalidate()` early-returns unless the tool is a write tool, so nothing in deprovisioning, token revocation, credential update, or connection delete evicts anything. But **it is not an authorisation bypass** — every cache hit still runs `injectCredentials` and `enforceToolCall` first, so a deprovisioned or deactivated user is refused before the lookup — and caching is enabled for only four vendors (`connectwise-psa`, `autotask`, `connectwise-cpq`, `itglue`), with credential-plaintext tools non-cacheable by construction. The real exposure is a still-authorised caller reading data fetched with a since-rotated credential.

  **Eight documents already carried an accurate correction and were deliberately left alone** (`cipp`, `domotz`, `huntress`, `liongard`, `saas-alerts`, `sentinelone`, `syncro`, `threatlocker`). Two carried an inaccurate one and were fixed by hand: `checkpoint-avanan` claimed "the gateway handles the refresh", but Harmony Email is key-based to Conduit — the hourly Infinity-portal token is minted by the **connector container** from the stored client id and secret, not by Conduit's OAuth machinery; and `connectwise-cpq` led with the overstated sentence while its own follow-on about the write-once private key was worth keeping.

  **Two things could not be verified and are recorded rather than papered over.** `warmly` **has no vendor entry in Conduit at all** — it appears only in an internal audit dataset — so its plugin documents a connector Conduit cannot broker today; it received the key-based wording, which is true of every vendor regardless. And `xero`'s existing first bullet says Xero Custom Connections "mint 30-minute tokens with no refresh token", but Conduit's actual Xero entry is standard authorisation-code OAuth requesting `offline_access`, which is precisely the scope that yields a refresh token. That bullet was left as-is rather than rewritten from a neighbouring claim, and is flagged here for a follow-up.

  `_templates/governance-template.md` is updated too, since it is the source of future copies: it now carries the accurate revocation wording and, for rotation, instructs the author to check `oauthConfig` and pick the matching line — with **"do not promise a rotate action, Conduit has none for any vendor"** stated explicitly. 53 plugins patch-bumped.

- **`checkpoint-avanan`'s agents and commands finish the correction started in #192 and #195 — and the four commands that named no tools turned out to be the worst of the set.** The skills and `GOVERNANCE.md` were rewritten against the real 13-tool `hec_*` surface in the earlier passes; `agents/` and `commands/` were left with the identical defect. All phantom `avanan_*` names are now gone from the plugin, and the plugin bumps to 0.4.0.

  **The commands' defect was not tool names — it was invented HTTP endpoints, which the name-based drift audit cannot see.** `search-threats`, `check-threat`, `search-quarantine` and `release-quarantine` named no MCP tools at all, so they passed every automated check; each instead documented a REST call that does not exist. `GET /v1.0/threats?...`, `GET /v1.0/threats/<id>`, `GET /v1.0/threats/<id>/iocs`, `GET /v1.0/threats/<id>/timeline`, `GET /v1.0/quarantine?...` and `POST /v1.0/quarantine/release` are all fabrications. The real server exposes `POST /v1.0/event/query`, `GET /v1.0/event/{id}`, `POST /v1.0/search/query`, `GET /v1.0/search/entity/{id}` and `POST /v1.0/action/entity`. **A command written generically is not a safe command; it is an unaudited one**, and the four here were teaching impossible workflows more confidently than the agents that at least named checkable tools.

  **The invented parameters mattered more than the invented paths, because several of them encode capabilities the product does not have.** `release-quarantine` offered `--allow-list`, `--notify` and `--reason`: the restore action accepts only ids and an optional `entityType`, there is no release-with-allow-list (releasing a message and creating an exception are two separate tools), and nothing on this surface notifies a recipient. It also reported success synchronously — but every quarantine and restore returns one `taskId` per entity and reports *acceptance*, so the command as written taught an agent to report an intention as an outcome. `search-quarantine` filtered on a `reason` enum (`PHISHING`/`MALWARE`/`SPAM`/`BEC`/`POLICY`/`BULK`) when **Harmony Email exposes no quarantine-reason field at all** — the reason is the detection, which lives on the event object, not the entity. `search-threats` offered `bec`, `ato`, `ransomware`, `spam` and `zero-day` types; the real enum has none of them (BEC and targeted phishing arrive as `phishing`, ransomware as `malware`), and its `false-positive` status does not exist because no tool transitions an event into a closed state. The skill template and `_standards/skill-quality-checklist.md` now define an optional `## Anti-triggers` section placed immediately after the overview, where every bullet must name the destination skill to load instead. **Deliberately optional**: the checklist already requires that sections holding only boilerplate be omitted, so a bullet that merely negates `when_to_use` is filler and is cut — hit rates across the fleet ranged from 40% (huntress) to 97% (workflow packs) depending on how much vocabulary a plugin genuinely shares with its neighbours. Separately, `_templates/governance-template.md` adds a per-plugin `GOVERNANCE.md`: what the plugin authenticates as, its tools grouped by **blast radius rather than HTTP verb**, and a recommended agent policy (read autonomously, propose writes, never self-approve destructive calls), written for an MSP owner deciding what to let an agent do against a live production tenant. Because authentication is brokered centrally at the Conduit gateway rather than held per-technician, these documents cover tool permission tiers and what central brokering buys (no local secrets, one-place rotation, per-operator audit identity, revocation that actually revokes) instead of local secret handling. Worked exemplar shipped on `huntress`, including the classification of `huntress_incidents_bulk_approve` as destructive — approving a SOC remediation instructs Huntress to act on a customer endpoint, so it is not the bookkeeping change its verb implies. `huntress` bumped to 0.3.0
